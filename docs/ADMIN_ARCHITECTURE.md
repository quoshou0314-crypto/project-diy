# 後台架構規劃

範圍:訂單、商品、行銷、折扣券、賣場設定五個後台模組,支撐它們的後端 API 與資料模型,以及前台的 SEO。
現況:只有前台估價頁(`frontend/`),商品、促銷、折扣券都寫死在 `frontend/src/data.ts`,計價在 `frontend/src/pricing.ts` 模擬。

標了「**預設**」的地方是我先替你選的做法,列在最後的[待確認決策](#12-待確認決策),改了會影響哪些部分也寫在那裡。

## 1. 整體架構

```
project-diy/
├── frontend/   前台(已存在,要擴充)    → 估價頁之外,新增商品頁、分類頁等可被搜尋的頁面
├── admin/      後台管理介面(新)        → 讀寫 /api/admin/*
├── workers/
│   ├── public/   公開 Worker(新)       → 產生前台頁面、目錄、試算、網站地圖。拿不到加密金鑰
│   └── secure/   受保護 Worker(新)     → 會員、訂單、後台。持有加密金鑰,自己驗證登入
└── shared/     共用程式(新)            → 型別(由 frontend/src/types.ts 搬來)、計價引擎
```

整套系統跑在 Cloudflare 上,沒有自己管理的主機。

| 層 | 選擇 | 理由 |
|---|---|---|
| 後端 | Cloudflare Workers(TypeScript) | 與前台同語言,`types.ts`、`pricing.ts` 可直接搬過去用;自動擴展,不用管主機 |
| 資料庫 | Cloudflare D1(SQLite) | 沒有對外的連線位址,只有綁定的 Worker 讀寫得到 |
| 前台頁面 | 由公開 Worker 在伺服器端產生 HTML,再由瀏覽器接手互動 | 搜尋引擎拿到的就是完整內容。見[第 11 節](#11-seo) |
| 後台頁面 | Workers 靜態資源 | 後台不需要被搜尋到。頁面本身不含資料,資料全部來自需要登入的後台 API |
| 圖片 | Cloudflare R2 | 商品圖是公開資料,經 Cloudflare 快取提供 |
| 排程 | Workers Cron Triggers | 個資到期清除、定期匯出備份 |
| 登入(會員與後台人員) | Worker 自己做 email 驗證碼 | 同一套驗證機制,兩種身分分開發登入狀態。不用 Cloudflare Access:它以人數計費,不適合公開會員;既然驗證已經自己做,後台也不必再多接一套 |
| 金流、物流 | 綠界 ECPay(信用卡、ATM、超商代碼;超商取貨、宅配) | 卡號在綠界的頁面輸入,不經過我們的系統。綠界在 Cloudflare 帳號之外,是必須信任的對象 |
| 寄信(驗證碼、通知) | Cloudflare Email Service | 在同一個 Cloudflare 帳號內,由 Worker 直接綁定,沒有另外的 API 金鑰要保管。目前是測試版,需付費方案:每月含 3,000 封,之後每 1,000 封 0.35 美元 |

### 撐得住多少流量

| | 免費方案 | 付費方案 |
|---|---|---|
| Worker 請求數 | 每天 10 萬次(約 3,000 位訪客,每人約 30 次請求) | 無上限,自動擴展 |
| 每次請求的 CPU 時間 | 10 毫秒 | 預設 30 秒 |
| D1 單一資料庫容量 | 500 MB | 10 GB(不能再加) |

- **需要付費方案。** 寄信服務只在付費方案提供;受保護 Worker 每個請求都要驗證登入、加解密個資,免費方案的 10 毫秒也偏緊。
- **瓶頸在 D1,不在 Worker。** 每個 D1 資料庫一次只處理一個查詢:查詢平均 1 毫秒時約每秒 1,000 次。
- **流量大的路徑不碰資料庫。** 目錄與促銷整份快取(庫存狀態短時間快取,實際數量以下單當下為準),試算直接用快取計算;只有驗證折扣券與下單才查資料庫。一張訂單寫十幾列,零組件店的訂單量離上限差好幾個數量級。
- **10 GB 夠用很久。** 圖片在 R2 不佔資料庫;訂單個資到期會清除。
- **後台報表不直接掃訂單表。** D1 一次只跑一個查詢,慢查詢會卡住同時間的下單。總覽頁的營業額與熱門商品由排程每天算進彙總表,頁面只讀彙總。
- **資料庫存取集中在一層**,SQL 不散在各處。將來 D1 不夠用時可以換資料庫,其餘程式不動。
- **D1 辦不了限量搶購。** 幾千人同一秒結帳會讓寫入排隊甚至回過載錯誤。目前不做;若將來要辦,名額的發放交給 Durable Object(在記憶體裡依序扣名額),搶到的人才進入一般下單流程寫入 D1。列在最後一個階段。

貫穿所有模組的原則:

1. **金額一律由後端算。** 前台只顯示 `/api/quote` 的結果(`pricing.ts` 開頭的註解已經是這個方向)。折扣券清單不能再出現在前台程式碼裡,否則任何人都看得到所有券號。
2. **訂單存快照。** 訂單成立時把品名、單價、折扣明細整份複製進訂單,之後商品改價、促銷下架都不影響舊訂單。
3. **金額用整數新台幣、含稅。** 與目前 `Product.price` 一致。
4. **會員只存在後端,後台沒有會員模組。** 見[第 4 節的會員](#會員)。
5. **個資盡可能加密保存。** 見[第 8 節](#8-個資保護)。
6. **信任邊界是擁有者本人的 Cloudflare 帳號權限,其他路徑一律擋住。** 見[第 9 節](#9-安全邊界)。
7. **每個商品、分類都有自己的網址與完整的 HTML。** 見[第 11 節](#11-seo)。

## 3. 商品

### 資料表

| 表 | 主要欄位 | 說明 |
|---|---|---|
| `categories` | `id`、`name`、`group`、`sort`、`enabled`、`slug`、`intro`、`seo_title`、`seo_description` | 對應現在的 `Category`;`group` 是下拉頁籤名稱 |
| `spec_defs` | `category_id`、`key`、`label`、`unit`、`type`(文字/數字)、`sort`、`system` | 對應 `SpecDef`。`system = true` 的欄位被相容性檢查用到,後台不可刪除或改 key |
| `brands` | `id`、`name`、`sort` | 現在是商品上的字串,獨立成表才能避免「ASUS / Asus / 華碩」並存 |
| `products` | `id`、`code`、`category_id`、`brand_id`、`name`、`price`、`status`、`stock_qty`、`allow_backorder`、`low_stock_at`、`shipping_class`、`description`、`specs`(JSON)、`sort`、`slug`、`seo_title`、`seo_description`、`mpn`(原廠型號)、`gtin`(商品條碼) | `code` 是對外短代號,見下方 |
| `product_images` | `product_id`、`url`、`alt`、`width`、`height`、`sort` | 第一張當清單縮圖;`alt` 是圖片的文字說明 |
| `stock_movements` | `product_id`、`delta`、`reason`(進貨/下單保留/取消釋放/退貨入庫/盤點調整)、`order_id`、`actor`、`note`、`created_at` | 每一次數量變動都有一筆,庫存數永遠對得回來 |
| `price_history` | `product_id`、`old_price`、`new_price`、`changed_by`、`changed_at` | 每次改價自動寫入 |

### 設計重點

- **商品代號要穩定。** 分享連結 `#m=c3.1-m2.1` 直接用商品 id。後端主鍵改用流水號,另外保留 `code`(`c3`、`m2`)給網址用,建立後不可修改,否則顧客存下來的估價連結會失效。
- **上下架與庫存分開。** `status`:草稿 / 上架 / 下架(下架後前台看不到,但舊連結打開時要能顯示「此商品已下架」)。庫存由 `stock_qty` 決定,前台顯示「有現貨」「剩 N 件」「可調貨」「缺貨」。
- **庫存在下單當下保留。** 訂單成立時扣 `stock_qty` 並寫一筆異動;未付款逾期或取消時加回來。這樣不會有兩個人買到同一件。
- **扣庫存不能超賣。** 資料表限制 `stock_qty` 不得小於 0,扣到負數時整批寫入失敗、訂單不成立,顧客看到「庫存不足」。同時下單的情況要寫測試。
- **可調貨的商品**(`allow_backorder`)庫存為 0 仍可下單,前台標示「調貨,約需 N 天」;這類商品不受上一條限制,另記欠貨數量。
- **低庫存提醒。** 數量低於 `low_stock_at` 時列入後台清單,並可寄信通知店長。
- **只能透過「進貨」與「盤點調整」改數量**,不能直接編輯數字,每次都要填原因。
- **原廠型號與商品條碼**(`mpn`、`gtin`)是 Google 用來辨識「這是哪一個商品」的依據,會放進結構化資料與商品資料檔。零組件幾乎都有,建檔時就填。
- **`shipping_class`**:小件(可超商取貨)或大件(只能宅配或自取)。見第 4 節的物流。
- **批次改價是必要功能。** 零組件報價變動頻繁,逐筆改不實際。提供「匯出 CSV → 修改 → 匯入」(價格與進貨數量都可以),匯入前先顯示差異清單讓人確認。D1 每次請求的查詢數有上限,匯入以批次寫入,一次上限先訂 2,000 筆。
- **相容性規則先留在程式碼。** 目前只有兩條(處理器與主機板腳位、主機板與機殼尺寸),依賴 `socket`、`form` 兩個規格 key。規則數量少時做成後台可編輯不划算;只要用 `system` 旗標保護這些 key 即可。

## 4. 訂單

目前前台只有「分享」和「列印」,沒有送出流程,所以這個模組前後台都要新增。

### 流程

```
顧客:估價單 → 登入 → 選物流(超商選門市 / 宅配填地址 / 自取)→ 選付款 → 成立訂單(保留庫存)
                                                                        │
                                                                        ▼ 導向綠界付款頁
  待付款 ──► 已付款 ──► 備貨/組裝中 ──► 已出貨 ──► 已到店/已送達 ──► 已完成
    │           │                          │
    │           └──► 退款中 ──► 已退款       └──► 未取退回 ──► 退貨入庫
    └──► 逾期未付,自動取消並釋放庫存
```

- **訂單狀態只由三種來源推進**:綠界的付款通知、綠界的物流通知、後台人員的操作(出貨、退款、完成)。顧客的瀏覽器回到網站時顯示的「付款成功」只是畫面,不改變訂單狀態。
- **成立後不能改單。** 已付款的訂單要改內容,做法是退款後重新下單,金額與庫存才對得起來。
- **超商取貨付款**(到店付現)時沒有線上付款這一步:訂單成立後直接進入備貨,顧客取貨時付款,由綠界的物流通知確認。

### 會員

會員用 email 驗證碼登入,由受保護 Worker 自己處理,不經過後台。沒有密碼,沒有註冊步驟。後台人員用同一套驗證碼機制,差異見[第 7 節](#帳號與權限)。

1. 顧客按「登入」或「送出訂單」,輸入 email。
2. Worker 產生六位數驗證碼,經 Cloudflare Email Service 寄出。
3. 顧客輸入驗證碼。正確的話,Worker 建立登入狀態並發 cookie;這個 email 第一次出現時自動建立會員紀錄。
4. 登出:Worker 刪除登入狀態並清掉 cookie。

| 表 | 主要欄位 |
|---|---|
| `members` | `id`、`email_hash`(用來比對)、`email`(加密)、`created_at`、`last_login_at` |
| `login_codes` | `audience`(會員/後台)、`email_hash`、`code_hash`、`expires_at`、`attempts`、`created_at` |
| `sessions` | `token_hash`、`member_id`、`expires_at`、`created_at` |
| `admin_sessions` | `token_hash`、`admin_user_id`、`expires_at`、`created_at`、`last_seen_at` |

登入這段是自己寫的程式,下面每一條都是必要的限制:

- **驗證碼 10 分鐘內有效,只能用一次,最多輸錯 5 次**,超過就作廢,要重新申請。
- **同一個 email 60 秒內只能申請一次,每小時有上限;同一來源位址也有上限**,避免被用來轟炸別人的信箱或猜驗證碼。
- **不管 email 是否已是會員,回應都一樣**(「驗證碼已寄出」),不讓人探測誰是會員。
- **驗證碼與登入憑證在資料庫只存雜湊**,資料庫外流也無法拿來登入。
- **登入 cookie 設為 HttpOnly、Secure、SameSite**,前台程式讀不到;會改資料的請求另外檢查來源網域。
- **登入狀態有效 30 天**(**預設**),到期重新收驗證碼。過期的驗證碼與登入狀態由排程清除。

其他原則:

- **瀏覽與試算不需登入,送出訂單才需要。** 估價與分享連結維持現在的體驗。
- **只存識別身分所需的最少資料**,不存密碼、不存個人檔案。
- **email 加密保存,只用來寄驗證碼與通知信**,不出現在後台畫面上。
- **`members` 沒有任何後台 API。** `/api/admin/*` 底下不提供會員的列表、查詢或修改。

### 金流(綠界)

1. 訂單成立後,Worker 產生付款表單並導向綠界的付款頁。顧客在綠界的頁面選擇並完成付款,**卡號不經過我們的系統,也不會存下來**。
2. 綠界從它的伺服器通知 `POST /api/gateway/ecpay/payment`。Worker 依序檢查:簽章正確、交易編號存在、金額與訂單相符、這筆通知沒有處理過,全部通過才把訂單改成已付款。
3. ATM 與超商代碼是先取號、後付款:取號通知到達時把帳號或代碼顯示給顧客,付款完成時再收到一次通知。

- **支援的付款方式**:信用卡一次付清、ATM 虛擬帳號、超商代碼、超商取貨付款。分期之後再評估。
- **付款期限**:信用卡 30 分鐘、ATM 3 天、超商代碼 7 天(**預設**,在賣場設定可調)。逾期由排程取消訂單、釋放庫存、退回折扣券次數。
- **每次付款用新的交易編號**,顧客付款失敗後可以重試,不會撞號。
- **退款**:**預設**由店長在綠界的後台操作,再到我們的後台把訂單標記為已退款並填寫原因。依綠界文件,信用卡退款的 API 只能全額退且測試環境不能用,所以第一版不串接。

### 物流(綠界)

| 方式 | 適用 | 寄送資訊 |
|---|---|---|
| 超商取貨(7-ELEVEN、全家、萊爾富、OK) | 整張訂單都是小件,且符合超商的材積重量限制 | 姓名、手機、門市 |
| 宅配 | 任何訂單 | 姓名、手機、地址 |
| 到店自取 | 任何訂單 | 姓名、手機 |

1. **選門市**:顧客在結帳頁按「選擇門市」,導向綠界的電子地圖,選好後綠界把門市代號與名稱傳回,Worker 驗證後帶回結帳頁。
2. **出貨**:後台人員在訂單按「出貨」,Worker 向綠界建立物流訂單,取得物流編號與寄件代碼,後台可列印託運單。
3. **追蹤**:綠界把到店、取貨、逾期未取等狀態通知 `POST /api/gateway/ecpay/logistics`,Worker 驗證簽章後更新 `shipments` 並寄信通知顧客。

- **零組件大多不能走超商。** 依綠界賣家文件,超商包裹的限制約為三邊合計 105 公分以內、最長邊 45 公分以內、5 公斤以內(各超商略有不同,以綠界後台公告為準)。機殼、螢幕、整機一定超過;顯示卡、電源、主機板要看包裝。所以每個商品要標 `shipping_class`,訂單裡只要有一件大件,結帳頁就不提供超商取貨。
- **多件小件合併後也可能超過限制。** 第一版用簡單規則:小件數量超過設定值(**預設** 3 件)就不提供超商取貨。
- **取貨付款有金額上限**,確切數字我沒有查到官方資料,實作前要向綠界確認;超過上限的訂單不提供取貨付款。
- **超商取貨的收件人要填真實姓名**(取貨時核對證件),手機號碼要是 09 開頭的十碼,結帳頁要檢查並提示。
- **未取退回**:包裹退回後由後台人員確認入庫,庫存加回;線上已付款的訂單由店長決定退款或重寄。
- **組裝服務的整機**只能宅配或自取。

### 綠界通知的處理原則

- **只信簽章,不信來源。** 兩個通知端點是公開的,任何人都打得到;沒有通過簽章驗證的請求一律拒絕並記錄。
- **重複通知不重複處理。** 綠界收不到回覆會重送,同一筆通知處理第二次時只回覆成功,不再改狀態。
- **回覆格式固定**,處理完成才回覆成功;處理失敗就不回成功,讓綠界重送。
- **金鑰**(特店編號對應的 HashKey、HashIV)存成受保護 Worker 的機密設定。金流與物流的簽章演算法不同,要用綠界文件的範例值寫測試。
- **先在綠界的測試環境完整走過**每一種付款方式與每一家超商,再切到正式環境。

### 設計重點

- **後台訂單只顯示必要的寄送資訊**:物流方式、收件人姓名、收件電話、取貨門市或宅配地址。姓名、電話、地址加密保存,列表上遮罩顯示(見[第 8 節](#8-個資保護))。這些是顧客送出訂單時填的,屬於這張訂單,不是會員資料。後台 API 回傳訂單時不帶會員的 email 或其他會員欄位,店員無法從訂單反查會員。
- **成立訂單時重新計價。** `POST /api/orders` 只收「商品代號 + 數量 + 券號 + 物流與付款方式 + 寄送資訊」,後端自己算金額,不採用前台送來的數字;送給綠界的金額也是後端算的這個數字。若與顧客畫面上的金額不同(剛好改價或活動結束),回傳新報價讓顧客確認後再送一次。
- **訂單、庫存保留、折扣券使用次數在同一批寫入內完成**,任何一項失敗就全部不成立。
- **顧客登入後在前台查自己的訂單**(`GET /api/me/orders`),只看得到自己的。
- **聯絡顧客的管道**:狀態變更由後端自動寄信到會員 email;需要直接聯繫時用訂單上的收件電話。
- **發票資訊不在這一版**。綠界也有電子發票服務,連同統編、抬頭欄位之後再做。

## 7. 賣場設定

綠界的金鑰不在這裡,存成 Worker 的機密設定,只有擁有者能更換。其餘設定用一張 `settings` 表(`key` + `value` JSON)存放,因為每一項都只有一筆、欄位又各不相同。

| 分頁 | 內容 | 誰會讀 |
|---|---|---|
| 基本資料 | 店名、Logo、電話、LINE、地址、營業時間 | 前台頁首頁尾、列印的估價單、通知信 |
| 取貨與運送 | 啟用哪些物流方式與超商、各方式運費、滿額免運門檻、組裝服務費、超商取貨的小件數量上限、寄件人資料 | 計價引擎、結帳頁、建立物流訂單 |
| 付款方式 | 啟用哪些付款方式、各方式的付款期限、取貨付款的金額上限 | 結帳頁、逾期取消排程 |
| 訂單規則 | 估價有效天數、訂單編號前綴、促銷與折扣券能否並用 | 計價引擎、訂單模組 |
| SEO 與分享 | 標題格式、預設描述、預設分享圖、網站圖示、網址轉址表、退換貨與運送政策、待補資料清單 | 前台每一頁的 `<head>`、網站地圖 |
| 通知 | 新訂單與低庫存通知店家的信箱、各狀態通知顧客的信件內容 | 訂單模組 |
| 帳號與權限 | 後台帳號、角色 | 見下 |

### 帳號與權限

這裡管的是後台人員。後台登入與會員登入用同一套 email 驗證碼機制,但身分完全分開:

- **只有 `admin_users` 裡啟用中的 email 才會收到後台驗證碼。** 其他 email 申請時得到一樣的回應,但不會寄信,也無從登入。這張表就是後台的白名單。
- **後台與會員的登入狀態分開存、分開發 cookie。** 後台 cookie 只對 `/admin` 與 `/api/admin` 路徑有效;會員的登入狀態對後台 API 無效,反過來也是。同一個 email 可以同時是會員和後台人員,要各登入一次。
- **後台的限制比會員嚴**:登入狀態 12 小時到期(**預設**),閒置 1 小時自動登出;驗證碼輸錯上限與申請頻率更低。
- **每次後台登入寫入 `audit_logs`**;停用某位人員時,同時刪除他所有的登入狀態,立即生效。
- **第一位店長的 email 在部署設定裡指定**,之後的人員由店長在後台新增。沒有密碼,系統不存任何密碼。

| 表 | 主要欄位 |
|---|---|
| `admin_users` | `email`、`name`、`role`、`enabled`、`last_login_at` |
| `audit_logs` | `actor_id`、`action`、`target_type`、`target_id`、`diff`、`created_at` |

**預設**兩種角色就夠:**店長**(全部功能)與**店員**(訂單、商品;不能動行銷、折扣券、賣場設定、帳號)。改價、改促銷、改設定都寫入 `audit_logs`,金額出問題時查得到是誰在什麼時候改的。

## 8. 個資保護

### 哪些欄位加密

系統裡的個資只有下面這幾項,全部在受保護 Worker 寫入資料庫前逐欄加密(AES-256-GCM),資料庫裡只有密文。

| 資料 | 欄位 | 保存方式 |
|---|---|---|
| 會員 email | `members.email` | 加密 |
| 會員 email(比對用) | `members.email_hash`、`login_codes.email_hash` | 雜湊(HMAC),登入時用來找到會員,無法還原 |
| 驗證碼、登入憑證 | `login_codes.code_hash`、`sessions.token_hash`、`admin_sessions.token_hash` | 雜湊 |
| 收件人姓名 | `orders.recipient_name` | 加密 |
| 收件電話 | `orders.recipient_phone` | 加密,另存一欄雜湊供搜尋 |
| 宅配地址 | `orders.address` | 加密 |
| 顧客備註 | `orders.customer_note` | 加密(顧客可能在裡面寫電話或地址) |

商品、促銷、折扣券、訂單金額與明細不是個資,維持明文,後台的搜尋、排序、報表才做得動。

### 金鑰

- **金鑰存成受保護 Worker 的機密設定**,只有這個 Worker 執行時讀得到。公開 Worker 沒有綁定金鑰,只看得到密文。金鑰不放在資料庫,不進版本庫。
- **機密設定寫入後無法再讀出來**,連帳號擁有者在控制台也看不到值。所以金鑰產生當下就要另外離線保存一份(列印或存在不連網的媒體);弄丟的話,加密的個資永遠解不開。
- **加密用與雜湊用是兩把不同的金鑰。**
- **每筆密文帶金鑰版本號**,之後可以換金鑰:新資料用新金鑰,舊資料由排程逐批重新加密。

### 交給綠界的個資

金流與物流必須把部分資料交給綠界,這些資料離開後就不在我們的加密與清除範圍內:

| 用途 | 交出的資料 | 不交出的 |
|---|---|---|
| 付款 | 交易編號、金額、商品名稱摘要 | 會員 email、收件資訊。商品名稱只送「DIY 零組件一批」這類摘要,不送明細 |
| 超商取貨 | 收件人姓名、手機、門市 | email、地址 |
| 宅配 | 收件人姓名、手機、地址 | email |

- **`shipments.store_id` 與門市名稱不加密**:單獨一個門市不足以識別個人,後台也需要用它出貨。
- **到期清除只清得到我們這邊**。綠界那邊的保存期限依綠界的規定。隱私權說明要寫明資料會提供給綠界用於付款與配送。

### 加密帶來的限制

- **電話只能完整比對。** 後台輸入完整號碼,後端算出雜湊後比對;無法用「末三碼」或部分號碼搜尋。
- **姓名、地址不能搜尋。** 找訂單用訂單編號、日期、狀態。
- **email 不能搜尋。** 會員登入靠 email 的雜湊比對。

### 減少個資的存在與曝光

- **到期清除。** 訂單完成或取消滿一定天數(**預設** 180 天)後,排程把收件人姓名、電話、地址、備註清空;訂單的商品與金額保留供帳務與報表使用。
- **後台預設遮罩。** 訂單列表顯示「王○明、0912-•••-678」,進入訂單詳情按下「顯示」才解密,每次顯示寫入 `audit_logs`(誰、何時、哪張訂單)。
- **列印與匯出。** 出貨單需要完整收件資訊,列印視同一次顯示並留下紀錄;訂單匯出檔預設不含個資欄位。
- **日誌不寫個資。** 伺服器日誌、錯誤回報、`audit_logs` 的差異內容都排除上述欄位。
- **會員可以刪除帳號。** 刪除時清掉 email、email 雜湊與所有登入狀態;已成立的訂單保留,但其上的寄送資訊一併清空。

## 9. 安全邊界

原則:**信任邊界就是擁有者本人的 Cloudflare 帳號權限。** 唯一的例外是綠界:收錢與配送必須交給它,見下方「仍然必須信任的對象」。 能改程式、讀資料、動金鑰、改入口規則的,只有用這個帳號登入的你本人;帳號沒有其他成員,也不把權限交給任何外部服務。除了下面一條入口,其他進得來的路全部關掉。

### 唯一的入口

```
顧客 / 店員的瀏覽器
        │ HTTPS(自訂網域)
        ▼
   Cloudflare 邊緣(頻率限制)
        ├─ 目錄、試算 ───────► 公開 Worker ────► D1(只讀目錄、促銷;驗證折扣券)
        │                                        無金鑰
        ├─ 綠界的付款/物流通知 ─► 受保護 Worker(驗證綠界簽章)
        └─ 會員與後台路徑 ───► 受保護 Worker ──► D1、R2、寄信、呼叫綠界
                               自己驗證登入         持有金鑰
                               (會員、後台各一套登入狀態)
```

### 擋住的路

| 路徑 | 做法 |
|---|---|
| 不經自訂網域打 Worker | 關閉 `workers.dev` 網址與預覽網址,Worker 只掛在自訂網域,頻率限制才不會被繞過 |
| 拿會員身分打後台 | 會員的登入狀態對 `/api/admin/*` 無效;後台只認後台的登入狀態,且每個請求都確認 `admin_users` 的紀錄仍啟用、角色有權限 |
| 猜驗證碼、轟炸信箱 | 見第 4 節的登入限制;另在 Cloudflare 對登入路徑設定頻率限制 |
| 從網路連資料庫 | D1 沒有連線位址也沒有密碼,只有綁定的 Worker 與帳號權限碰得到 |
| 偽造付款或物流通知 | 通知端點只認綠界的簽章,並核對金額與訂單;簽章金鑰只在受保護 Worker |
| 目錄與試算的漏洞讀到個資 | 流量最大的公開 Worker 沒有金鑰,就算被利用也只拿得到密文 |
| 後台密碼 | 不存在。後台只能用白名單上的 email 收驗證碼登入 |
| 直接讀圖片儲存 | R2 不開公開存取,圖片經 Worker 提供並由 Cloudflare 快取 |
| 用 API 憑證操作帳號 | 不建立任何長期 API 憑證。沒有憑證放在版本庫、自動化服務或別人手上 |
| 由外部服務部署 | 不接受。版本庫平台沒有部署權限,見下方「部署」 |
| 其他帳號成員 | 沒有。帳號只有擁有者一人 |

### 帳號內的權限劃分

| 身分 | 能做的 | 不能做的 |
|---|---|---|
| 公開 Worker | 讀 D1 的目錄與促銷、驗證折扣券、讀 R2 圖片 | 讀金鑰 |
| 受保護 Worker | 讀寫 D1、讀金鑰、寫 R2、寄信 | — |
| 擁有者(你) | 全部:部署、機密設定、D1、R2、網域與頻率限制規則 | — 這就是信任邊界 |
| 後台人員 | 以白名單上的 email 登入後台,依角色操作訂單與商品 | 碰不到 Cloudflare 帳號;看個資要按「顯示」並留紀錄 |

- **帳號啟用兩步驟驗證,建議用實體安全金鑰**,並保存好復原碼。帳號被盜等於邊界失守。
- **帳號綁定的信箱同樣重要**,能收這個信箱的人可以重設帳號密碼,信箱也要開兩步驟驗證。
- **定期檢視帳號的稽核紀錄**:登入、規則變更、API 憑證建立。正常情況下不該出現任何 API 憑證。

### 部署

能部署受保護 Worker 的人,等於能讓新程式讀到金鑰,所以部署只能由帳號擁有者本人執行。

- **只從你自己的電腦部署**:用你的 Cloudflare 帳號登入部署工具後執行,不經過任何自動化服務。
- **版本庫只存程式碼,沒有部署權限**,因此不在信任邊界內。版本庫被入侵不會直接改到線上的程式;但你部署前要確認拉下來的是自己認得的版本。
- **你的電腦因此在邊界內**:部署工具的登入狀態存在電腦上。電腦要有磁碟加密與螢幕鎖,不用時登出部署工具。
- 套件版本鎖定,更新前檢視;受保護 Worker 的相依套件越少越好。

### 備份

- D1 內建時間點還原,用來應付誤刪與誤改。
- 另由排程定期把資料庫匯出到 R2 的私有儲存桶。匯出檔裡的個資本來就是密文,金鑰不在其中。
- 金鑰的離線備份是還原的必要條件,見第 8 節。

### 後台不再有外層的門

改成自己驗證之後,後台登入頁直接面對網際網路,前面沒有 Access 這道獨立的檢查。換來的是不依賴人數計費、只有一套驗證機制要維護;代價是**後台的安全完全取決於這段自己寫的登入程式**。因此:

- 登入程式要有完整的測試:過期、重複使用、輸錯上限、頻率限制、會員與後台互不通用。
- Cloudflare 對 `/api/admin/auth/*` 設更嚴的頻率限制。
- 後台登入通知:每次後台登入寄一封通知信給店長,異常登入能馬上發現。
- 目前只靠 email:後台人員的信箱被盜就等於後台被登入,所以後台人員的信箱要開兩步驟驗證。日後可加驗證器 App 的動態碼作為第二道,不需改動現有登入流程。

### 仍然必須信任的對象

「其他路都擋住」做得到的是不留多餘的入口,但下面幾項無法排除在外:

- **Cloudflare 本身。** 程式、資料庫、金鑰、身分驗證都在它上面,HTTPS 也在它那裡解開。逐欄加密防的是公開 Worker 的漏洞與匯出檔外流,**防不了 Cloudflare 平台本身**。這是全部上 Workers 與自管主機最大的差別。
- **綠界。** 它確認錢有沒有付、包裹到了沒,也拿得到收件人姓名、手機與地址。綠界的帳號(特店後台)可以退款與查交易,要和 Cloudflare 帳號同等級保管並開兩步驟驗證。綠界的簽章金鑰外流,別人就能偽造「已付款」通知。
- **顧客的信箱服務。** 驗證碼與通知信寄出後就在顧客的信箱裡。信件內容不放收件地址與電話。
- **受保護 Worker 的程式與套件。** 它們讀得到金鑰。

### 擋得住與擋不住的

擋得住:從網路直接攻擊資料庫、繞過登入、公開端點的漏洞、資料庫匯出檔外流、版本庫或後台人員帳號被入侵後想碰金鑰或改程式。
擋不住:你的 Cloudflare 帳號或部署用的電腦被盜用、受保護 Worker 本身的漏洞與惡意套件、被盜用的信箱。後台人員的信箱被盜,對方進得了後台,靠遮罩、顯示紀錄與到期清除限制損害範圍;會員的信箱被盜,對方看得到那位會員自己的訂單與寄送資訊。

## 10. 計價引擎與 API

### 計價順序

把 `pricing.ts` 的 `quote()` 搬到後端,順序維持不變,並補上運費:

```
原價小計
 → 單品折扣
 → 合購折扣
 → 滿額折        (門檻以扣完前兩項後的金額判斷)
 → 折扣券        (門檻以扣完前三項後的金額判斷,限一張)
 → 加運費與組裝費  (運費依物流方式;滿額免運以折扣後金額判斷)
 = 應付金額      (不低於 0)
```

引擎寫成純函式,放在 `shared/`,兩個 Worker 共用:輸入「購物內容 + 當下有效的商品、促銷、券、設定」,輸出報價。`/api/quote` 與成立訂單都呼叫同一個函式,試算與實際金額才會一致,也容易寫測試。相容性提醒(`warnings`)一併由它回傳。

## 11. SEO

### 現況的問題

- **整個網站只有一個網址。** 商品沒有自己的頁面,估價內容放在網址的 `#` 後面,搜尋引擎不會把它當成不同的頁面。
- **內容由瀏覽器端的程式產生。** 伺服器回傳的 HTML 是空殼,搜尋引擎與社群分享的預覽抓不到商品名稱與價格。

所以 SEO 不是事後加標籤,而是前台的頁面結構要改。

### 目前進度

前台已先做完不需要後端的部分(資料仍是 `data.ts` 的示意資料):

| 項目 | 狀態 |
|---|---|
| 首頁、分類、商品各有網址(畫面沿用估價工具與商品詳情疊加框),建置時輸出完整 HTML | 已完成 |
| 每頁的標題、描述、正式網址、分享預覽 | 已完成(由資料自動產生;後台逐頁覆寫要等後台) |
| 結構化資料:商品、麵包屑、商品清單、網站名稱 | 已完成(庫存、運費、退貨、店家資料要等後台與賣場設定) |
| 網站地圖、抓取規則、找不到頁面 | 已完成 |
| 站內連結:分類頁籤、品名連到商品網址;商品詳情底部的商品卡連到相容零件與同類商品 | 已完成(品牌頁、麵包屑暫不做) |
| 未設定正式網域時全站標示不收錄 | 已完成(建置時以 `VITE_SITE_URL` 指定網域,見 `frontend/.env.example`) |
| 推薦菜單、說明頁、圖片、轉址表、商品資料檔、Google 帳號 | 未做,依實作順序進行 |

前台的原則是**原有畫面不動**:估價工具的外觀與操作和改版前相同,改的是搜尋引擎看得到的部分(網址、HTML、`<head>`)。沒有新增任何版面:商品的網址打開的就是原本的商品詳情疊加框,只是它現在有自己的網址、標題與結構化資料。

**商品網址的 HTML 只含該商品的內容。** 直接由商品網址進來時(搜尋結果、分享連結),背後的分類清單先不畫,所以每個商品頁的內容各自獨立,不會夾帶同分類的整份清單;分類再大,商品頁也不會跟著變重。訪客關閉詳情框(×、Esc、點框外、加入估價單)後才畫出清單,接著就是一般的分類頁;站內點開的疊加框不受影響,清單本來就在。這對所有訪客都一樣,不是對搜尋引擎另給一份內容。

**商品詳情底部有商品卡。** 先列搭配得起來的零件(處理器列同腳位主機板,主機板列處理器與裝得下的機殼,機殼列裝得下的主機板),再列同類的其他商品。卡片和格狀清單用的是同一種,可以直接加入估價單,點品名則換到那個商品。這些卡片在商品網址的 HTML 裡,所以每個商品頁都連到相關的商品。

**仍然存在的限制**:商品自己的內容量就是詳情框裡的描述與規格。目前描述是示意文字、沒有圖片,內容偏少;排名要靠之後在後台填入真正的描述、圖片與規格。

| 頁面 | 網址 | 是否給搜尋引擎 |

- **只有一個正式網域**,其餘(有無 `www`、`http`)一律轉過去。

| 表 | 主要欄位 |
|---|---|
| `redirects` | `from_path`、`to_path`、`created_at` |

### 伺服器端產生頁面

- **公開 Worker 直接回傳完整的 HTML**:標題、描述、商品名稱、價格、規格表、庫存狀態都在裡面,瀏覽器載入後再接手互動(加入估價單、篩選)。
- **頁面內容來自目錄快取,不逐次查資料庫**,所以被搜尋引擎大量抓取也不會壓到 D1。
- **整頁在 Cloudflare 邊緣快取**,商品或價格在後台更新時清除對應頁面的快取。
- **現有的 React 元件沿用**,同一套元件在伺服器與瀏覽器各跑一次。實作方式見決策 10。

### 每一頁的標題、描述與分享預覽

- **標題與描述有預設格式,可逐頁覆寫。** 例如商品頁預設「AMD Ryzen 7 9800X3D 處理器|店名」,描述由品牌、主要規格、價格組成;後台可替個別商品、分類、推薦菜單另外填寫。
- **分享預覽**:每頁都有分享用的標題、描述與圖片,貼到 LINE、Facebook 時顯示商品圖與價格。
- **每頁標明正式網址**,同一內容不會被當成多個頁面。
- **頁面語言標示為台灣繁體中文。**

### 結構化資料

讓搜尋結果直接顯示價格、庫存、路徑:

| 頁面 | 標記內容 |
|---|---|
| 商品頁 | 商品名稱、圖片、品牌、原廠型號、商品條碼、售價與原價(新台幣)、是否有貨、促銷到期日、運費與送達時間、退貨政策 |
| 分類頁、推薦菜單 | 商品清單 |
| 所有頁面 | 麵包屑路徑(首頁 › 處理器 › 商品) |
| 首頁、關於我們 | 店家資料:店名、地址、電話、營業時間、Logo(取自賣場設定) |
| 首頁 | 網站名稱(搜尋結果上顯示的店名) |
| 文章(之後) | 標題、作者、發布與更新日期、圖片 |

- **標記的價格與庫存必須和頁面上顯示的一致**,都從同一份目錄資料產生。不一致會被搜尋引擎視為誤導。
- **不標記沒有的東西**:目前沒有評價功能,就不放評分。
- **運費與退貨政策取自賣場設定**,和結帳頁、說明頁顯示的是同一份。
- **每次上版前用 Google 的複合式搜尋結果測試工具檢查**商品頁、分類頁、首頁各一頁。

### 網站地圖與抓取規則

- **`/sitemap.xml` 由公開 Worker 產生**,列出所有上架商品、分類、品牌、推薦菜單、說明頁與各自的最後更新時間。
- **`/robots.txt`** 指向網站地圖,並排除結帳、會員、後台與 API。這些頁面的回應另外加上不收錄的標頭。
- **不擋 Google 的爬蟲。** Cloudflare 的機器人防護與我們自己的頻率限制都要放行經驗證的搜尋引擎爬蟲;被擋住的頁面不會被收錄。前台頁面不設頻率限制,限制只加在登入、結帳與 API。
- **給爬蟲和給訪客的內容完全相同**,不做差別顯示。
- **狀態碼要正確**:找不到的頁面回「找不到」,不能回一個顯示「查無商品」的正常頁面;永久搬家的回永久轉址。
- **頁面帶最後更新時間**,沒變動時爬蟲可以略過,把抓取額度留給有更新的頁面。
- **連結都是真的連結。** 分類、分頁、商品之間的導覽用一般超連結,不是只靠程式處理的按鈕;分類頁的分頁有各自的網址。
- **下架或缺貨的商品不直接消失。**

| 商品狀態 | 頁面處理 |
|---|---|
| 缺貨 | 頁面保留,標示缺貨 |
| 停售(下架) | 頁面保留,標示已停售並推薦同分類的替代商品;從網站地圖移除 |
| 永久刪除 | 回應「已移除」,讓搜尋引擎盡快拿掉 |

### 速度

速度是排名因素,也直接影響手機使用者:

- **圖片**:上傳時在後台產生多種尺寸與較小的格式,頁面依螢幕大小載入;圖片標明寬高,避免載入時版面跳動;首屏以外的圖片延後載入。
- **商品圖一定要有文字說明**,預設用「品牌 + 品名」,可在後台修改。
- **前台不放第三方的追蹤程式。** 流量統計用 Cloudflare Web Analytics:不用 cookie、不追蹤個人,而且在你的 Cloudflare 帳號內,不違反信任邊界。
- **以 Google 的三項網頁體驗指標為驗收標準**(手機版):主要內容 2.5 秒內顯示、點擊後 0.2 秒內有反應、版面位移分數 0.1 以下。上線前用工具量測,上線後看 Search Console 裡真實使用者的數據。
- **以手機版為準。** Google 用手機版頁面決定排名,手機上看得到的內容、連結、結構化資料要和桌面版一樣完整。
- **互動程式分開載入。** 商品頁只載入商品頁需要的程式,不把整個估價工具一起送下去。

### 圖片搜尋

- **商品主圖至少 1200 像素寬**,並允許搜尋結果顯示大圖預覽。
- **圖片網址用可讀的檔名**(品牌與型號),不是亂碼。
- **圖片列入網站地圖**,每個商品頁附上它的圖片。
- **說明文字**預設「品牌 + 品名」,可在後台修改。

### 網站名稱與圖示

- 首頁標記網站名稱,搜尋結果才會顯示店名而不是網域。
- 提供正方形的網站圖示(48 像素的倍數),搜尋結果的每一筆旁邊都會顯示。

### 站內連結

站內連結決定搜尋引擎怎麼理解頁面之間的關係,也把權重帶到重要的頁面:

- **商品頁連到相容的零件。** 既有的相容性資料可以直接用:處理器頁列出同腳位的主機板,主機板頁列出裝得下的機殼。這是一般賣場沒有、對 DIY 使用者又真的有用的連結。
- **商品頁連到包含它的推薦菜單**,推薦菜單連到每一個零件。
- **每頁都有麵包屑**,並連回分類與品牌。
- **每一頁都連到所有分類。** 類別頁籤全部直接列出,一排放不下就折到下一排,沒有下拉;每個分類在每一頁的 HTML 裡都有連結。

### 商家可信度

Google 會看這家店是不是真實、可聯絡、政策清楚的商家,Merchant Center 也要求:

- **必備頁面**:關於我們、聯絡方式(電話、地址、營業時間)、運送說明、退換貨政策、隱私權說明、服務條款。內容取自賣場設定,只維護一份。
- **全站 HTTPS**,並強制瀏覽器只用 HTTPS 連線。
- **店名、地址、電話在網站、結構化資料、Google 商家檔案三處完全一致。**

### 內容

技術只是讓頁面能被收錄,能不能排到前面要靠內容:

- **推薦菜單**是最貼近搜尋意圖的頁面(「三萬 電腦 配備」「遊戲主機 菜單」),每一份菜單要有說明文字,不只是零件清單。
- **分類頁的導言**(`categories.intro`):一兩段說明怎麼挑,而不是只有商品列表。
- **商品描述不要只貼原廠文字。** 與其他賣場完全相同的描述很難排到前面。
- **文章**(選購指南、相容性教學)效果最好但最花人力,列在最後一個階段。

### Google 的三個帳號

這三項不是程式,是要在 Google 那邊開設與維護的帳號。它們在 Cloudflare 帳號之外,但裡面只有公開的商品與店家資料,沒有顧客個資;所用的 Google 帳號要開兩步驟驗證。

| 服務 | 用途 | 我們要做的 |
|---|---|---|
| Search Console | 看收錄狀況、搜尋字詞、網頁體驗、結構化資料錯誤 | 以網域方式驗證(在 Cloudflare 的 DNS 加一筆紀錄)、提交網站地圖 |
| Merchant Center | 購物分頁與商品區塊的免費刊登 | 公開 Worker 產生商品資料檔 `/feeds/google.xml`:名稱、連結、圖片、價格、庫存、品牌、型號、條碼、運費;填寫運送與退貨設定 |
| 商家檔案 | 地圖與在地搜尋 | 建立並驗證實體店面、填營業時間與網站連結、放店面照片;請顧客留評價 |

- **商品資料檔的價格與庫存必須和商品頁一致。** 兩者由同一份目錄產生,並每天更新;不一致的商品會被 Merchant Center 停止刊登。
- **商家檔案只在有實體店面時適用**,見決策 12。

### 持續檢查

上線不是結束。每月檢視一次 Search Console:

- 沒被收錄的頁面與原因。
- 結構化資料與商品資料檔的錯誤。
- 網頁體驗指標有沒有退步。
- 哪些搜尋字詞有曝光但點擊少(改標題與描述)、哪些字詞排在第二頁(補內容)。

後台的「SEO 與分享」提供一份清單:缺少描述、缺少圖片說明、缺少型號或條碼、描述過短的商品,讓店員知道該補哪些。
