# 後台架構規劃

範圍:訂單、商品、行銷、折扣券、賣場設定五個後台模組,以及支撐它們的後端 API 與資料模型。
現況:只有前台估價頁(`frontend/`),商品、促銷、折扣券都寫死在 `frontend/src/data.ts`,計價在 `frontend/src/pricing.ts` 模擬。

標了「**預設**」的地方是我先替你選的做法,列在最後的[待確認決策](#10-待確認決策),改了會影響哪些部分也寫在那裡。

---

## 1. 整體架構

```
project-diy/
├── frontend/   前台估價頁(已存在)      → 讀 /api/catalog、/api/quote、送出 /api/orders、會員登入
├── admin/      後台管理介面(新)        → 讀寫 /api/admin/*
├── backend/    API 伺服器(新)          → 計價引擎、訂單、會員、後台權限
└── shared/     前後台共用的型別(新)    → 由 frontend/src/types.ts 搬過來擴充
```

| 層 | 預設選擇 | 理由 |
|---|---|---|
| 後端 | Node.js + TypeScript(Fastify) | 與前台同語言,`types.ts`、`pricing.ts` 可直接搬過去用 |
| 資料庫 | PostgreSQL | 訂單需要交易;商品規格每個分類不同,用 JSONB 欄位存最省事 |
| 後台介面 | React + Vite(與前台同一套) | 不必多學一套工具;後台與前台分開打包,後台程式碼不會送到顧客瀏覽器 |
| 圖片 | 物件儲存(S3 相容) | 資料庫只存網址 |
| 會員登入 | 第三方 email 認證(**預設** Google 登入) | 不自己存密碼、不自己寄驗證信;後端只驗證第三方發的憑證 |

三條貫穿所有模組的原則:

1. **金額一律由後端算。** 前台只顯示 `/api/quote` 的結果(`pricing.ts` 開頭的註解已經是這個方向)。折扣券清單不能再出現在前台程式碼裡,否則任何人都看得到所有券號。
2. **訂單存快照。** 訂單成立時把品名、單價、折扣明細整份複製進訂單,之後商品改價、促銷下架都不影響舊訂單。
3. **金額用整數新台幣、含稅。** 與目前 `Product.price` 一致。
4. **會員只存在後端,後台沒有會員模組。** 見[第 4 節的會員](#會員)。
5. **個資盡可能加密保存。** 見[第 8 節](#8-個資保護)。

## 3. 商品

### 資料表

| 表 | 主要欄位 | 說明 |
|---|---|---|
| `categories` | `id`、`name`、`group`、`sort`、`enabled` | 對應現在的 `Category`;`group` 是下拉頁籤名稱 |
| `spec_defs` | `category_id`、`key`、`label`、`unit`、`type`(文字/數字)、`sort`、`system` | 對應 `SpecDef`。`system = true` 的欄位被相容性檢查用到,後台不可刪除或改 key |
| `brands` | `id`、`name`、`sort` | 現在是商品上的字串,獨立成表才能避免「ASUS / Asus / 華碩」並存 |
| `products` | `id`、`code`、`category_id`、`brand_id`、`name`、`price`、`status`、`stock_status`、`description`、`specs`(JSONB)、`sort` | `code` 是對外短代號,見下方 |
| `product_images` | `product_id`、`url`、`sort` | 第一張當清單縮圖 |
| `price_history` | `product_id`、`old_price`、`new_price`、`changed_by`、`changed_at` | 每次改價自動寫入 |

### 設計重點

- **商品代號要穩定。** 分享連結 `#m=c3.1-m2.1` 直接用商品 id。後端主鍵改用流水號,另外保留 `code`(`c3`、`m2`)給網址用,建立後不可修改,否則顧客存下來的估價連結會失效。
- **狀態分兩個欄位。** `status`:草稿 / 上架 / 下架(下架後前台看不到,但舊連結打開時要能顯示「此商品已下架」)。`stock_status`:有現貨 / 需調貨 / 缺貨。**預設**不做數量庫存,零組件店多半是調貨,數量很難維持正確。
- **批次改價是必要功能。** 零組件報價變動頻繁,逐筆改不實際。提供「匯出 CSV → 修改 → 匯入」,匯入前先顯示差異清單讓人確認。
- **相容性規則先留在程式碼。** 目前只有兩條(處理器與主機板腳位、主機板與機殼尺寸),依賴 `socket`、`form` 兩個規格 key。規則數量少時做成後台可編輯不划算;只要用 `system` 旗標保護這些 key 即可。

## 4. 訂單

目前前台只有「分享」和「列印」,沒有送出流程,所以這個模組前後台都要新增。

### 流程

```
顧客:估價單 → 登入(第三方 email 認證)→ 填寄送資訊 → 送出
                                        │
                                        ▼
      待確認 ──► 已確認 ──► 已付款 ──► 備貨/組裝中 ──► 可取貨/已出貨 ──► 已完成
        │           │          │
        └───────────┴──────────┴──► 已取消(已付款的要記錄退款)
```

**預設**:送出後由店家確認貨況與價格,再通知顧客付款(轉帳或到店付)。線上金流放在第二階段,屆時「已確認 → 已付款」改由金流回呼自動推進,其餘不變。

### 會員

會員由前台直接對後端登入,整個流程不經過後台。

1. 顧客在前台按登入,導向第三方完成 email 認證。
2. 前台把第三方發的憑證交給 `POST /api/auth/login`,後端向第三方驗證後建立登入狀態。
3. 第一次登入時後端自動建立會員紀錄,沒有另外的註冊步驟。

| 表 | 主要欄位 |
|---|---|
| `members` | `id`、`provider`、`provider_subject`(第三方的使用者識別碼)、`email`、`created_at`、`last_login_at` |

- **瀏覽與試算不需登入,送出訂單才需要。** 估價與分享連結維持現在的體驗。
- **後端只存識別身分所需的最少資料**,不存密碼、不存個人檔案。
- **email 加密保存,只給後端寄通知信用**,不出現在後台畫面上。
- **`members` 沒有任何後台 API。** `/api/admin/*` 底下不提供會員的列表、查詢或修改。

### 資料表

| 表 | 主要欄位 |
|---|---|
| `orders` | `no`(訂單編號)、`member_id`、`status`、`payment_status`、`fulfillment`(自取/宅配)、`recipient_name`、`recipient_phone`、`address`(宅配才有)、`need_assembly`、`subtotal`、`discount_total`、`shipping_fee`、`total`、`coupon_code`、`customer_note` |
| `order_items` | `order_id`、`product_id`、`code`、`name`、`brand`、`category_name`、`list_price`、`unit_price`、`qty`、`line_total` — 全部是快照 |
| `order_discounts` | `order_id`、`source_type`(促銷/折扣券/手動)、`source_id`、`label`、`amount` — 快照 |
| `order_events` | `order_id`、`type`、`from_status`、`to_status`、`note`、`actor`、`created_at` — 狀態變更、改單、內部備註都記在這裡 |

### 設計重點

- **後台訂單只顯示必要的寄送資訊**:取貨方式、收件人姓名、收件電話、宅配地址。這三個欄位加密保存,列表上遮罩顯示(見[第 8 節](#8-個資保護))。這些是顧客送出訂單時填的,屬於這張訂單,不是會員資料。後台 API 回傳訂單時不帶會員的 email 或其他會員欄位,店員無法從訂單反查會員。
- **成立訂單時重新計價。** `POST /api/orders` 只收「商品代號 + 數量 + 券號 + 寄送資訊」,後端自己算金額,不採用前台送來的數字。若與顧客畫面上的金額不同(剛好改價或活動結束),回傳新報價讓顧客確認後再送一次。
- **待確認階段可以改單。** 常見情況是某個零件缺貨,要換同級品。改單 = 重新計價 + 寫一筆 `order_events`。店家另外議價的部分用「手動調整」折扣列表示,不直接改總額,明細才對得起來。
- **顧客登入後在前台查自己的訂單**(`GET /api/me/orders`),只看得到自己的。
- **聯絡顧客的管道**:狀態變更由後端自動寄信到會員 email;需要直接聯繫(例如缺貨換料)時用訂單上的收件電話。
- **發票資訊不在這一版**,連同電子發票串接放到第五階段。

## 5. 行銷(促銷活動)

現有三種型別沿用,補上後台管理需要的欄位。

| 表 | 主要欄位 |
|---|---|
| `promotions` | `id`、`type`、`label`、`params`(JSONB)、`starts_at`、`ends_at`、`enabled`、`sort` |

| `type` | `params` | 對應現在的 |
|---|---|---|
| `item` 單品折扣 | `{ productId, off }` | `{ type: 'item', productId, off }` |
| `bundle` 合購折扣 | `{ categoryIds: [], off }` | `{ type: 'bundle', cats, off }` |
| `threshold` 滿額折 | `{ min, off }` | `{ type: 'threshold', min, off }` |

### 設計重點

- **活動狀態由時間推算**:未開始 / 進行中 / 已結束 / 已停用,不另存狀態欄位,避免排程漏跑造成狀態與時間不一致。
- **同一商品同時只能有一個進行中的單品折扣**,後台儲存時檢查時段是否重疊。
- **合購折扣每張訂單只折一次**,與目前 `pricing.ts` 的行為相同(買兩顆處理器、兩張主機板也只折一次)。
- **第二階段**:推薦菜單(店家排好整機組合,本質上就是一條存在後台的估價連結,加上名稱與說明)、前台公告列。

## 6. 折扣券

| 表 | 主要欄位 |
|---|---|
| `coupons` | `code`(唯一,不分大小寫)、`label`、`kind`(固定金額/百分比)、`value`、`cap`、`min_spend`、`starts_at`、`ends_at`、`usage_limit`、`per_customer_limit`、`enabled` |
| `coupon_redemptions` | `coupon_id`、`order_id`、`member_id`、`amount`、`created_at` |

### 設計重點

- **使用次數在成立訂單的同一筆交易內扣**,避免最後一張券被兩個人同時用掉。訂單取消時退回。
- **每人限用次數以會員判斷。** 後台的使用紀錄只列訂單編號、金額與時間,不顯示是哪位會員。
- **試算時不洩漏券的存在。** `/api/quote` 對「查無此券」「已過期」「已用完」的回應要一致地有限,並對同一來源的嘗試次數設上限,避免被猜券號。
- **一張訂單限用一張券**,與目前前台相同。
- **第二階段**:限定分類或商品適用、批次產生一次性券號。

## 7. 賣場設定

用一張 `settings` 表(`key` + `value` JSONB)存放,因為每一項都只有一筆、欄位又各不相同。

| 分頁 | 內容 | 誰會讀 |
|---|---|---|
| 基本資料 | 店名、Logo、電話、LINE、地址、營業時間 | 前台頁首頁尾、列印的估價單、通知信 |
| 取貨與運送 | 啟用哪些方式、運費、滿額免運門檻、組裝服務費 | 計價引擎、前台送出表單 |
| 付款方式 | 匯款帳號、到店付款說明;之後放金流金鑰 | 訂單確認信 |
| 訂單規則 | 估價有效天數、訂單編號前綴、促銷與折扣券能否並用 | 計價引擎、訂單模組 |
| 通知 | 新訂單通知店家的信箱、各狀態通知顧客的信件內容 | 訂單模組 |
| 帳號與權限 | 後台帳號、角色 | 見下 |

### 帳號與權限

這裡管的是後台人員,與會員是兩套完全分開的帳號與登入。

| 表 | 主要欄位 |
|---|---|
| `admin_users` | `email`、`password_hash`、`name`、`role`、`enabled`、`last_login_at` |
| `audit_logs` | `actor_id`、`action`、`target_type`、`target_id`、`diff`、`created_at` |

**預設**兩種角色就夠:**店長**(全部功能)與**店員**(訂單、商品;不能動行銷、折扣券、賣場設定、帳號)。改價、改促銷、改設定都寫入 `audit_logs`,金額出問題時查得到是誰在什麼時候改的。

## 8. 個資保護

### 哪些欄位加密

系統裡的個資只有下面這幾項,全部在後端寫入資料庫前逐欄加密(AES-256-GCM),資料庫裡只有密文。

| 資料 | 欄位 | 保存方式 |
|---|---|---|
| 會員 email | `members.email` | 加密 |
| 第三方識別碼 | `members.provider_subject` | 不存原值,只存雜湊(HMAC)。登入時只需要比對,不需要還原 |
| 收件人姓名 | `orders.recipient_name` | 加密 |
| 收件電話 | `orders.recipient_phone` | 加密,另存一欄雜湊供搜尋 |
| 宅配地址 | `orders.address` | 加密 |
| 顧客備註 | `orders.customer_note` | 加密(顧客可能在裡面寫電話或地址) |
| 後台人員密碼 | `admin_users.password_hash` | 單向雜湊(Argon2id),無法還原 |

商品、促銷、折扣券、訂單金額與明細不是個資,維持明文,後台的搜尋、排序、報表才做得動。

### 金鑰

- **金鑰不放在資料庫,也不進版本庫。** 由部署環境的金鑰管理服務或機密設定提供,只有後端程式讀得到。資料庫或備份單獨外洩時,拿到的只有密文。
- **加密用與雜湊用是兩把不同的金鑰。**
- **每筆密文帶金鑰版本號**,之後可以換金鑰:新資料用新金鑰,舊資料由背景工作逐批重新加密。

### 加密帶來的限制

- **電話只能完整比對。** 後台輸入完整號碼,後端算出雜湊後比對;無法用「末三碼」或部分號碼搜尋。
- **姓名、地址不能搜尋。** 找訂單用訂單編號、日期、狀態。
- **email 不需要搜尋。** 會員登入靠第三方識別碼的雜湊比對。

### 減少個資的存在與曝光

- **到期清除。** 訂單完成或取消滿一定天數(**預設** 180 天)後,排程把收件人姓名、電話、地址、備註清空;訂單的商品與金額保留供帳務與報表使用。
- **後台預設遮罩。** 訂單列表顯示「王○明、0912-•••-678」,進入訂單詳情按下「顯示」才解密,每次顯示寫入 `audit_logs`(誰、何時、哪張訂單)。
- **列印與匯出。** 出貨單需要完整收件資訊,列印視同一次顯示並留下紀錄;訂單匯出檔預設不含個資欄位。
- **日誌不寫個資。** 伺服器日誌、錯誤回報、`audit_logs` 的差異內容都排除上述欄位。
- **會員可以刪除帳號。** 刪除時清掉 email 與識別碼雜湊;已成立的訂單保留,但其上的寄送資訊一併清空。

### 傳輸與儲存環境

- 全站 HTTPS;後端到資料庫的連線也加密。
- 資料庫磁碟與備份啟用加密(與逐欄加密並行,兩層)。
- 會員與後台的登入狀態用 HttpOnly、Secure 的 cookie,前台程式讀不到。

### 這套做法擋得住與擋不住的

擋得住:資料庫被拖走、備份檔外流、有資料庫讀取權限的人直接查表。
擋不住:後端主機本身被入侵(金鑰在記憶體裡),或有權限的後台帳號被盜用。後者靠遮罩、顯示紀錄與到期清除來限制損害範圍,後台帳號另外建議啟用兩步驟驗證。

## 9. 計價引擎與 API

### 計價順序

把 `pricing.ts` 的 `quote()` 搬到後端,順序維持不變,並補上運費:

```
原價小計
 → 單品折扣
 → 合購折扣
 → 滿額折        (門檻以扣完前兩項後的金額判斷)
 → 折扣券        (門檻以扣完前三項後的金額判斷,限一張)
 → 加運費與組裝費
 = 應付金額      (不低於 0)
```

引擎寫成純函式:輸入「購物內容 + 當下有效的商品、促銷、券、設定」,輸出報價。`/api/quote`、成立訂單、後台改單都呼叫同一個函式,三處金額才會一致,也容易寫測試。相容性提醒(`warnings`)一併由它回傳。

### API

| 對象 | 路徑 | 用途 |
|---|---|---|
