# 後台架構規劃

範圍:訂單、商品、行銷、折扣券、賣場設定五個後台模組,以及支撐它們的後端 API 與資料模型。
現況:只有前台估價頁(`frontend/`),商品、促銷、折扣券都寫死在 `frontend/src/data.ts`,計價在 `frontend/src/pricing.ts` 模擬。

標了「**預設**」的地方是我先替你選的做法,列在最後的[待確認決策](#11-待確認決策),改了會影響哪些部分也寫在那裡。

---

## 1. 整體架構

```
project-diy/
├── frontend/   前台估價頁(已存在)      → 讀 /api/catalog、/api/quote、送出 /api/orders
├── admin/      後台管理介面(新)        → 讀寫 /api/admin/*
├── workers/
│   ├── public/   公開 Worker(新)       → 目錄、試算。拿不到加密金鑰
│   └── secure/   受保護 Worker(新)     → 會員、訂單、後台。持有加密金鑰,全部在 Access 後面
└── shared/     共用程式(新)            → 型別(由 frontend/src/types.ts 搬來)、計價引擎
```

整套系統跑在 Cloudflare 上,沒有自己管理的主機。

| 層 | 選擇 | 理由 |
|---|---|---|
| 後端 | Cloudflare Workers(TypeScript) | 與前台同語言,`types.ts`、`pricing.ts` 可直接搬過去用;自動擴展,不用管主機 |
| 資料庫 | Cloudflare D1(SQLite) | 沒有對外的連線位址,只有綁定的 Worker 讀寫得到 |
| 前台與後台頁面 | Workers 靜態資源 | 與 API 同網域,後台頁面放在 Access 後面 |
| 圖片 | Cloudflare R2 | 商品圖是公開資料,經 Cloudflare 快取提供 |
| 排程 | Workers Cron Triggers | 個資到期清除、定期匯出備份 |
| 登入(會員與後台人員) | Cloudflare Access(email 一次性驗證碼) | 不自己存密碼、不自己寄驗證信;Worker 只驗證 Access 簽發的憑證 |
| 寄通知信 | 外部寄信服務(待選,見決策 9) | Worker 不能直接寄信 |

### 撐得住多少流量

| | 免費方案 | 付費方案 |
|---|---|---|
| Worker 請求數 | 每天 10 萬次(約 3,000 位訪客,每人約 30 次請求) | 無上限,自動擴展 |
| 每次請求的 CPU 時間 | 10 毫秒 | 預設 30 秒 |
| D1 單一資料庫容量 | 500 MB | 10 GB(不能再加) |

- **建議直接用付費方案。** 受保護 Worker 每個請求都要驗證憑證、加解密個資,10 毫秒偏緊。
- **瓶頸在 D1,不在 Worker。** 每個 D1 資料庫一次只處理一個查詢:查詢平均 1 毫秒時約每秒 1,000 次。
- **流量大的路徑不碰資料庫。** 目錄與促銷整份快取,試算直接用快取計算;只有驗證折扣券與下單才查資料庫。一張訂單寫十幾列,零組件店的訂單量離上限差好幾個數量級。
- **10 GB 夠用很久。** 圖片在 R2 不佔資料庫;訂單個資到期會清除。

貫穿所有模組的原則:

1. **金額一律由後端算。** 前台只顯示 `/api/quote` 的結果(`pricing.ts` 開頭的註解已經是這個方向)。折扣券清單不能再出現在前台程式碼裡,否則任何人都看得到所有券號。
2. **訂單存快照。** 訂單成立時把品名、單價、折扣明細整份複製進訂單,之後商品改價、促銷下架都不影響舊訂單。
3. **金額用整數新台幣、含稅。** 與目前 `Product.price` 一致。
4. **會員只存在後端,後台沒有會員模組。** 見[第 4 節的會員](#會員)。
5. **個資盡可能加密保存。** 見[第 8 節](#8-個資保護)。
6. **安全邊界是 Cloudflare 帳號內的權限,其他路徑一律擋住。** 見[第 9 節](#9-安全邊界)。

## 3. 商品

### 資料表

| 表 | 主要欄位 | 說明 |
|---|---|---|
| `categories` | `id`、`name`、`group`、`sort`、`enabled` | 對應現在的 `Category`;`group` 是下拉頁籤名稱 |
| `spec_defs` | `category_id`、`key`、`label`、`unit`、`type`(文字/數字)、`sort`、`system` | 對應 `SpecDef`。`system = true` 的欄位被相容性檢查用到,後台不可刪除或改 key |
| `brands` | `id`、`name`、`sort` | 現在是商品上的字串,獨立成表才能避免「ASUS / Asus / 華碩」並存 |
| `products` | `id`、`code`、`category_id`、`brand_id`、`name`、`price`、`status`、`stock_status`、`description`、`specs`(JSON)、`sort` | `code` 是對外短代號,見下方 |
| `product_images` | `product_id`、`url`、`sort` | 第一張當清單縮圖 |
| `price_history` | `product_id`、`old_price`、`new_price`、`changed_by`、`changed_at` | 每次改價自動寫入 |

### 設計重點

- **商品代號要穩定。** 分享連結 `#m=c3.1-m2.1` 直接用商品 id。後端主鍵改用流水號,另外保留 `code`(`c3`、`m2`)給網址用,建立後不可修改,否則顧客存下來的估價連結會失效。
- **狀態分兩個欄位。** `status`:草稿 / 上架 / 下架(下架後前台看不到,但舊連結打開時要能顯示「此商品已下架」)。`stock_status`:有現貨 / 需調貨 / 缺貨。**預設**不做數量庫存,零組件店多半是調貨,數量很難維持正確。
- **批次改價是必要功能。** 零組件報價變動頻繁,逐筆改不實際。提供「匯出 CSV → 修改 → 匯入」,匯入前先顯示差異清單讓人確認。D1 每次請求的查詢數有上限,匯入以批次寫入,一次上限先訂 2,000 筆。
- **相容性規則先留在程式碼。** 目前只有兩條(處理器與主機板腳位、主機板與機殼尺寸),依賴 `socket`、`form` 兩個規格 key。規則數量少時做成後台可編輯不划算;只要用 `system` 旗標保護這些 key 即可。

## 4. 訂單

目前前台只有「分享」和「列印」,沒有送出流程,所以這個模組前後台都要新增。

### 流程

```
顧客:估價單 → 登入(Cloudflare Access 驗證 email)→ 填寄送資訊 → 送出
                                        │
                                        ▼
      待確認 ──► 已確認 ──► 已付款 ──► 備貨/組裝中 ──► 可取貨/已出貨 ──► 已完成
        │           │          │
        └───────────┴──────────┴──► 已取消(已付款的要記錄退款)
```

**預設**:送出後由店家確認貨況與價格,再通知顧客付款(轉帳或到店付)。線上金流放在第二階段,屆時「已確認 → 已付款」改由金流回呼自動推進,其餘不變。

### 會員

會員登入交給 Cloudflare Access,整個流程不經過後台,Worker 也不需要自己做登入頁。

Access 是擋在網站前面的一道門:指定哪些路徑要先通過驗證,通過後才把請求放進來,並在請求上附一張 Cloudflare 簽名的憑證。

| 路徑 | 是否經過 Access |
|---|---|
| 前台頁面、`/api/catalog`、`/api/quote` | 否,公開 |
| `/api/me/*`、`/api/orders`、`/account/*` | 是(會員),email 一次性驗證碼,任何 email 皆可 |
| `/admin/*`、`/api/admin/*` | 是(後台人員),email 一次性驗證碼,只允許白名單上的 email |

1. 顧客按「登入」或「送出訂單」,前台導向 `/account/login`。
2. Access 攔下請求,顯示驗證頁:顧客輸入 email,收信取得驗證碼,輸入後通過。
3. Access 導回原路徑。之後打到受保護路徑的每個請求,都帶有 `Cf-Access-Jwt-Assertion` 標頭。
4. 後端驗證這張憑證(簽章、簽發者、對應的應用程式代碼、有效期限),取出其中的使用者識別碼與 email。
5. 第一次見到的識別碼自動建立會員紀錄,沒有另外的註冊步驟。
6. 登出:前台導向 `/cdn-cgi/access/logout`。

| 表 | 主要欄位 |
|---|---|
| `members` | `id`、`access_subject`(Access 憑證裡的使用者識別碼)、`email`、`created_at`、`last_login_at` |

- **瀏覽與試算不需登入,送出訂單才需要。** 估價與分享連結維持現在的體驗。
- **後端只存識別身分所需的最少資料**,不存密碼、不存個人檔案。
- **email 加密保存,只給後端寄通知信用**,不出現在後台畫面上。
- **`members` 沒有任何後台 API。** `/api/admin/*` 底下不提供會員的列表、查詢或修改。
- **後端一律自己驗證憑證,不因為「請求是從 Cloudflare 來的」就信任。** 驗證用的公鑰會輪替,每次從 Cloudflare 的憑證端點取得並快取,不寫死在程式裡。
- **受保護 Worker 只掛在自訂網域的受保護路徑上**,預設的 `workers.dev` 網址與預覽網址都關閉,沒有不經 Access 的入口。見[第 9 節](#9-安全邊界)。
- **登入有效時間在 Access 設定**(**預設** 7 天),到期後顧客要重新收驗證碼。

**需要先確認的風險:Access 以人數計費。** 它原本是設計給公司內部人員用的,依 Cloudflare 官網,免費方案適用 50 人以下,超過為每人每月 7 美元。每個登入過的顧客都佔一個名額,拿來當公開會員登入,顧客一多就會超過免費額度。實際的計算方式與是否能釋出不活躍名額,要以你的 Cloudflare 帳號方案為準,見[待確認決策](#11-待確認決策) 2a。

### 資料表

| 表 | 主要欄位 |
|---|---|
| `orders` | `no`(訂單編號)、`member_id`、`status`、`payment_status`、`fulfillment`(自取/宅配)、`recipient_name`、`recipient_phone`、`address`(宅配才有)、`need_assembly`、`subtotal`、`discount_total`、`shipping_fee`、`total`、`coupon_code`、`customer_note` |
| `order_items` | `order_id`、`product_id`、`code`、`name`、`brand`、`category_name`、`list_price`、`unit_price`、`qty`、`line_total` — 全部是快照 |
| `order_discounts` | `order_id`、`source_type`(促銷/折扣券/手動)、`source_id`、`label`、`amount` — 快照 |
| `order_events` | `order_id`、`type`、`from_status`、`to_status`、`note`、`actor`、`created_at` — 狀態變更、改單、內部備註都記在這裡 |

### 設計重點

- **後台訂單只顯示必要的寄送資訊**:取貨方式、收件人姓名、收件電話、宅配地址。這三個欄位加密保存,列表上遮罩顯示(見[第 8 節](#8-個資保護))。這些是顧客送出訂單時填的,屬於這張訂單,不是會員資料。後台 API 回傳訂單時不帶會員的 email 或其他會員欄位,店員無法從訂單反查會員。
- **成立訂單時重新計價。** `POST /api/orders` 只收「商品代號 + 數量 + 券號 + 寄送資訊」,後端自己算金額,不採用前台送來的數字。若與顧客畫面上的金額不同(剛好改價或活動結束),回傳新報價讓顧客確認後再送一次。
- **待確認階段可以改單。** 常見情況是某個零件缺貨,要換同級品。改單 = 重新計價 + 寫一筆 `order_events`。店家另外議價的部分用「手動調整」折扣列表示,不直接改總額,明細才對得起來。
- **顧客登入後在前台查自己的訂單**(`GET /api/me/orders`),只看得到自己的。
- **聯絡顧客的管道**:狀態變更由後端自動寄信到會員 email;需要直接聯繫(例如缺貨換料)時用訂單上的收件電話。
- **發票資訊不在這一版**,連同電子發票串接放到第五階段。

## 5. 行銷(促銷活動)

現有三種型別沿用,補上後台管理需要的欄位。

| 表 | 主要欄位 |
|---|---|
| `promotions` | `id`、`type`、`label`、`params`(JSON)、`starts_at`、`ends_at`、`enabled`、`sort` |

| `type` | `params` | 對應現在的 |
|---|---|---|
| `item` 單品折扣 | `{ productId, off }` | `{ type: 'item', productId, off }` |
| `bundle` 合購折扣 | `{ categoryIds: [], off }` | `{ type: 'bundle', cats, off }` |
| `threshold` 滿額折 | `{ min, off }` | `{ type: 'threshold', min, off }` |

### 設計重點

- **活動狀態由時間推算**:未開始 / 進行中 / 已結束 / 已停用,不另存狀態欄位,避免排程漏跑造成狀態與時間不一致。
- **同一商品同時只能有一個進行中的單品折扣**,後台儲存時檢查時段是否重疊。
- **合購折扣每張訂單只折一次**,與目前 `pricing.ts` 的行為相同(買兩顆處理器、兩張主機板也只折一次)。
- **第二階段**:推薦菜單(店家排好整機組合,本質上就是一條存在後台的估價連結,加上名稱與說明)、前台公告列。

## 6. 折扣券

| 表 | 主要欄位 |
|---|---|
| `coupons` | `code`(唯一,不分大小寫)、`label`、`kind`(固定金額/百分比)、`value`、`cap`、`min_spend`、`starts_at`、`ends_at`、`usage_limit`、`per_customer_limit`、`enabled` |
| `coupon_redemptions` | `coupon_id`、`order_id`、`member_id`、`amount`、`created_at` |

### 設計重點

- **使用次數與訂單在同一批寫入內完成**,避免最後一張券被兩個人同時用掉。D1 沒有可以中途判斷的交易,做法是「整批成功或整批失敗」的批次加上條件式更新(剩餘次數大於 0 才扣),實作時要針對同時下單寫測試。訂單取消時退回。
- **每人限用次數以會員判斷。** 後台的使用紀錄只列訂單編號、金額與時間,不顯示是哪位會員。
- **試算時不洩漏券的存在。** `/api/quote` 對「查無此券」「已過期」「已用完」的回應要一致地有限,並對同一來源的嘗試次數設上限,避免被猜券號。
- **一張訂單限用一張券**,與目前前台相同。
- **第二階段**:限定分類或商品適用、批次產生一次性券號。

## 7. 賣場設定

用一張 `settings` 表(`key` + `value` JSON)存放,因為每一項都只有一筆、欄位又各不相同。

| 分頁 | 內容 | 誰會讀 |
|---|---|---|
| 基本資料 | 店名、Logo、電話、LINE、地址、營業時間 | 前台頁首頁尾、列印的估價單、通知信 |
| 取貨與運送 | 啟用哪些方式、運費、滿額免運門檻、組裝服務費 | 計價引擎、前台送出表單 |
| 付款方式 | 匯款帳號、到店付款說明;之後放金流金鑰 | 訂單確認信 |
| 訂單規則 | 估價有效天數、訂單編號前綴、促銷與折扣券能否並用 | 計價引擎、訂單模組 |
| 通知 | 新訂單通知店家的信箱、各狀態通知顧客的信件內容 | 訂單模組 |
| 帳號與權限 | 後台帳號、角色 | 見下 |

### 帳號與權限

這裡管的是後台人員。後台人員同樣經 Cloudflare Access 登入,但用的是另一個只允許白名單 email 的 Access 應用程式,與會員的憑證互不通用。系統沒有後台登入頁,也不存任何密碼。

| 表 | 主要欄位 |
|---|---|
| `admin_users` | `email`、`name`、`role`、`enabled`、`last_login_at` |
| `audit_logs` | `actor_id`、`action`、`target_type`、`target_id`、`diff`、`created_at` |

**預設**兩種角色就夠:**店長**(全部功能)與**店員**(訂單、商品;不能動行銷、折扣券、賣場設定、帳號)。改價、改促銷、改設定都寫入 `audit_logs`,金額出問題時查得到是誰在什麼時候改的。

要讓一個人進後台需要兩處都放行:Access 白名單有這個 email,而且 `admin_users` 裡有啟用中的對應紀錄。停用任何一處即失效。

## 8. 個資保護

### 哪些欄位加密

系統裡的個資只有下面這幾項,全部在受保護 Worker 寫入資料庫前逐欄加密(AES-256-GCM),資料庫裡只有密文。

| 資料 | 欄位 | 保存方式 |
|---|---|---|
| 會員 email | `members.email` | 加密 |
| Access 使用者識別碼 | `members.access_subject` | 不存原值,只存雜湊(HMAC)。登入時只需要比對,不需要還原 |
| 收件人姓名 | `orders.recipient_name` | 加密 |
| 收件電話 | `orders.recipient_phone` | 加密,另存一欄雜湊供搜尋 |
| 宅配地址 | `orders.address` | 加密 |
| 顧客備註 | `orders.customer_note` | 加密(顧客可能在裡面寫電話或地址) |

商品、促銷、折扣券、訂單金額與明細不是個資,維持明文,後台的搜尋、排序、報表才做得動。

### 金鑰

- **金鑰存成受保護 Worker 的機密設定**,只有這個 Worker 執行時讀得到。公開 Worker 沒有綁定金鑰,只看得到密文。金鑰不放在資料庫,不進版本庫。
- **機密設定寫入後無法再讀出來**,連帳號擁有者在控制台也看不到值。所以金鑰產生當下就要另外離線保存一份(列印或存在不連網的媒體);弄丟的話,加密的個資永遠解不開。
- **加密用與雜湊用是兩把不同的金鑰。**
- **每筆密文帶金鑰版本號**,之後可以換金鑰:新資料用新金鑰,舊資料由排程逐批重新加密。

### 加密帶來的限制

- **電話只能完整比對。** 後台輸入完整號碼,後端算出雜湊後比對;無法用「末三碼」或部分號碼搜尋。
- **姓名、地址不能搜尋。** 找訂單用訂單編號、日期、狀態。
- **email 不需要搜尋。** 會員登入靠 Access 使用者識別碼的雜湊比對。

### 減少個資的存在與曝光

- **到期清除。** 訂單完成或取消滿一定天數(**預設** 180 天)後,排程把收件人姓名、電話、地址、備註清空;訂單的商品與金額保留供帳務與報表使用。
- **後台預設遮罩。** 訂單列表顯示「王○明、0912-•••-678」,進入訂單詳情按下「顯示」才解密,每次顯示寫入 `audit_logs`(誰、何時、哪張訂單)。
- **列印與匯出。** 出貨單需要完整收件資訊,列印視同一次顯示並留下紀錄;訂單匯出檔預設不含個資欄位。
- **日誌不寫個資。** 伺服器日誌、錯誤回報、`audit_logs` 的差異內容都排除上述欄位。
- **會員可以刪除帳號。** 刪除時清掉 email 與識別碼雜湊;已成立的訂單保留,但其上的寄送資訊一併清空。

## 9. 安全邊界

原則:**唯一被信任的是 Cloudflare 帳號內的權限。** 系統沒有主機,所以「本機權限」對應到的是:誰能登入這個帳號、誰能部署 Worker、哪個 Worker 綁定了哪些資源。除了下面一條入口,其他進得來的路全部關掉。

### 唯一的入口

```
顧客 / 店員的瀏覽器
        │ HTTPS(自訂網域)
        ▼
   Cloudflare 邊緣
        ├─ 公開路徑 ───────────────► 公開 Worker ──► D1(只讀目錄、促銷;驗證折扣券)
        │                                            無金鑰
        └─ 受保護路徑 ─► Access 驗證 ─► 受保護 Worker ──► D1、R2
                                         持有金鑰
```

### 擋住的路

| 路徑 | 做法 |
|---|---|
| 繞過 Access 打 Worker | 關閉 `workers.dev` 網址與預覽網址,Worker 只掛在自訂網域。受保護 Worker 仍驗證每個請求的 Access 憑證,並核對是「會員」還是「後台」哪一個應用程式簽發的 |
| 從網路連資料庫 | D1 沒有連線位址也沒有密碼,只有綁定的 Worker 與帳號權限碰得到 |
| 公開端點的漏洞讀到個資 | 公開 Worker 沒有金鑰,就算被利用也只拿得到密文 |
| 後台密碼登入頁 | 不存在。後台只能經 Access 白名單進入 |
| 直接讀圖片儲存 | R2 不開公開存取,圖片經 Worker 提供並由 Cloudflare 快取 |
| 用帳號憑證直接操作資料 | 不建立能讀寫 D1 或機密設定的長期 API 憑證。唯一的 API 憑證是部署用的,權限只到「部署這兩個 Worker」 |
| 未經審核的部署 | 見下方「部署」 |

### 帳號內的權限劃分

| 身分 | 能做的 | 不能做的 |
|---|---|---|
| 公開 Worker | 讀 D1 的目錄與促銷、驗證折扣券、讀 R2 圖片 | 讀金鑰 |
| 受保護 Worker | 讀寫 D1、讀金鑰、寫 R2、寄信 | — |
| 部署用憑證 | 更新兩個 Worker 的程式 | 讀機密設定的值、改 Access 規則、改帳號成員 |
| 帳號擁有者 | 全部 | — 這就是安全邊界,人數越少越好 |

- **帳號成員只留必要的人**,全部啟用兩步驟驗證,擁有者建議用實體安全金鑰。
- **Access 規則、帳號成員、API 憑證的變更都看得到稽核紀錄**,定期檢視。

### 部署

能部署受保護 Worker 的人,等於能讓新程式讀到金鑰,所以部署權限就是邊界的一部分。

- **預設**:只從版本庫的主分支部署,主分支受保護、合併需要審核;部署憑證存在版本庫的受保護環境裡,每次部署要擁有者按核准。
- 這表示**版本庫的管理權限也在邊界內**,與 Cloudflare 帳號同等級保管。
- 套件版本鎖定,更新前檢視;受保護 Worker 的相依套件越少越好。

### 備份

- D1 內建時間點還原,用來應付誤刪與誤改。
- 另由排程定期把資料庫匯出到 R2 的私有儲存桶。匯出檔裡的個資本來就是密文,金鑰不在其中。
- 金鑰的離線備份是還原的必要條件,見第 8 節。

### 仍然必須信任的對象

「其他路都擋住」做得到的是不留多餘的入口,但下面幾項無法排除在外:

- **Cloudflare 本身。** 程式、資料庫、金鑰、身分驗證都在它上面,HTTPS 也在它那裡解開。逐欄加密防的是帳號內權限不足的人與匯出檔外流,**防不了 Cloudflare 平台本身**。這是全部上 Workers 與自管主機最大的差別。
- **版本庫平台。** 因為部署從那裡發動。
- **寄信服務。** 寄通知信那一刻會員 email 會離開 Cloudflare。信件內容不放收件地址與電話。
- **受保護 Worker 的程式與套件。** 它們讀得到金鑰。

### 擋得住與擋不住的

擋得住:從網路直接攻擊資料庫、繞過登入、公開端點的漏洞、資料庫匯出檔外流、有資料庫讀取權限但不能部署的人查表。
擋不住:帳號擁有者或能核准部署的人、受保護 Worker 本身的漏洞、被盜用的後台人員信箱(Access 驗證碼寄到信箱)。最後一項靠遮罩、顯示紀錄與到期清除限制損害範圍。

## 10. 計價引擎與 API

### 計價順序

把 `pricing.ts` 的 `quote()` 搬到後端,順序維持不變,並補上運費:

```
原價小計
 → 單品折扣
 → 合購折扣
 → 滿額折        (門檻以扣完前兩項後的金額判斷)
 → 折扣券        (門檻以扣完前三項後的金額判斷,限一張)
 → 加運費與組裝費
 = 應付金額      (不低於 0)
```

引擎寫成純函式,放在 `shared/`,兩個 Worker 共用:輸入「購物內容 + 當下有效的商品、促銷、券、設定」,輸出報價。`/api/quote`、成立訂單、後台改單都呼叫同一個函式,三處金額才會一致,也容易寫測試。相容性提醒(`warnings`)一併由它回傳。

### API

| 對象 | 路徑 | 用途 | Worker |
|---|---|---|---|
| 前台 | `GET /api/catalog` | 分類、規格、上架商品、進行中的單品折扣(要顯示在商品卡上)、賣場公開資料 | 公開 |
| 前台 | `POST /api/quote` | 試算:`{ items, coupon }` → 報價 | 公開 |
| 前台(需登入) | `GET /api/me` | 目前登入的會員。登入與登出由 Cloudflare Access 處理,系統沒有登入 API | 受保護 |
| 前台(需登入) | `POST /api/orders` | 送出訂單 | 受保護 |
| 前台(需登入) | `GET /api/me/orders` | 會員查自己的訂單 | 受保護 |
| 後台 | `GET /api/admin/me` | 目前登入的後台人員與角色。登入與登出由 Cloudflare Access 處理 | 受保護 |
| 後台 | `/api/admin/orders`、`/products`、`/categories`、`/brands`、`/promotions`、`/coupons`、`/settings`、`/users` | 各模組的列表、新增、修改 | 受保護 |
| 後台 | `POST /api/admin/orders/:id/transition` | 狀態變更(後端檢查是否為允許的轉換) | 受保護 |
| 後台 | `POST /api/admin/products/import` | 批次改價 | 受保護 |

前台改動:`data.ts` 換成讀 `/api/catalog`;`pricing.ts` 換成呼叫 `/api/quote`(輸入停頓後才送出,避免每按一次數量就打一次);新增會員登入、送出訂單的表單、「我的訂單」頁。
